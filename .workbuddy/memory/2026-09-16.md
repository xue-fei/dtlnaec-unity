# 2026-09-16

## AEC 延迟更新门控（远端 VAD + 双讲检测）

借鉴 WebRTC AEC3 的延迟更新门控思想 + 参考 sherpa-onnx 项目 TenVad 的滞回 VAD 设计，
为 dtlnaec-unity 新增延迟更新门控，解决「远端静音/双讲时 GCC-PHAT 在噪声里瞎猜」的问题。

### 新增文件
- `Assets/dtlnaec-unity/Scripts/RealTest/SpeechActivityGate.cs`：纯 C# 能量自适应 VAD +
  双讲检测，输出 `AllowDelayUpdate` 门控。

### 核心设计（经过离线 Python 验证，6 个场景全部通过）
1. **能量自适应阈值**：底噪用「历史能量最小值」跟踪（非固定阈值），语音阈值 = 底噪 + 12dB。
2. **底噪冻结机制（关键坑）**：语音段底噪必须【完全冻结】，否则长时间持续语音会
   把底噪缓慢拉高，最终能量/底噪比值跌破阈值、语音被误判成静音。
   用 `NOISE_UP_RATIO=2.0` 区分「噪声波动(≤2×底噪)」和「语音(>2×底噪)」。
3. **底噪初始化窗口**：前 32 帧取能量最小值，避开「启动即在说话」时第一帧高能量污染底噪。
4. **滞回状态机**：MinSpeech=0.25s / MinSilence=0.5s；关键修正——静音帧让 speechTimer
   「缓慢衰减(×2速率)」而非立即归零，否则语音中的字间停顿会让「连续 0.25s」永远凑不齐。
5. **双讲检测**：近端 mic 和远端 loopback 各自独立 VAD，同时判「说话」即双讲，冻结延迟更新。

### 调试中发现的易错点（备忘）
- 能量比 dB 换算：`10^(dB/10)`（能量域），不是 `10^(dB/20)`（幅值域）。
- 底噪「能量 ≥ 底噪就极慢向上回归」是错的——长期语音会拉高底噪，必须冻结。
- 滞回「静音帧 speechTimer 归零」是错的——语音中的停顿会让阈值永远达不到。

### 接入点
`MicCapture.RunCalibration`：每帧 `_gate.ProcessFrame(lpbFrame, micFrame)` 更新状态，
`AllowDelayUpdate == false`（远端静音或双讲）时跳过 `UpdateDelay`，保持当前延迟。
